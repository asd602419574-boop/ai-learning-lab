# 同一审批系统的真实试学任务

状态：供真实学习者使用的试学方案，尚未执行真人试学，不是学习效果报告。本轮不开发新课程或第二套系统。

适用两条路线：业务/架构路线不要求编程；工程路线需能在指导下打开项目目录、编辑文本、运行Python命令。环境问题与知识问题分别记录，不把没有安装Python当作概念不理解。

## 学习者任务单

请先独立完成第一次判断，再查资料修订。可以查课程、自己的记录和官方文档；第一次不要展开完整参考补丁或复制示范。求助与参考使用如实记录，不作惩罚。

### 任务A：不看代码，解释边界

场景仍是企业资源审批：虚构员工为一次社区活动申请临时照明设备，金额6800元，希望标为紧急，理由是“原设备故障，今晚活动无法照常举行”。

先写预测，再用已有知识核对：

1. 紧急是否改变审批岗位？谁有权作出决定？哪些信息来自申请，哪些必须由服务端决定？
2. 原流程中的提交、校验、岗位分配、决定、通知/归档，哪些是本轮真实实现，哪些仍只是流程设计？
3. 若前端已经弹出“请填原因”，为什么仍要后端与数据库约束？
4. 用自己的图或文字把浏览器、HTTP、业务规则、SQLite、事件联系起来，指出一次201响应能证明什么、还缺什么。

交付：初次预测、核对后的修订及依据。不要只写术语定义或照抄课程关系图。

### 任务B：设计一份别人能实现的变更

仍采用normal/urgent及原因规则。使用自己的字段表、请求与验收表，说明：

- 缺字段、null、未知等级、空白原因的区别；正常响应与错误状态。
- 旧行/旧请求如何兼容；迁移中断与重启怎样处理；代码与数据库怎样成对恢复。
- 新字段经过哪些模块；哪些原有状态、权限与事务保证应保持。
- 设计至少一组与示范数值/标题不同的请求，列出HTTP与数据库预期，说明如何发现“201但未持久化”。

在V2.3成果区记录设计，刷新验证仍在。修改一条判断，确认旧提交变为待提交；重新提交并导出一份JSON。可把当前稿改成另一句话，再用文件预览确认恢复，核对恢复的是哪一版。

业务/架构路线可以在这里形成完整交付；下面工程任务按需选择。设计栏目齐全只表示可审查，语义仍需按依据复核。

### 任务C：独立改一次真实程序（工程路线）

创建自己命名的prepare副本，不使用demo作为自己的实现。先运行check并解释两项失败，再按设计修改实际代码、数据库迁移和前端。

使用不同于参考的虚构标题与成本中心，亲自完成：

1. 普通申请按旧请求提交；紧急申请提交并在GET与SQLite中核对两个字段。
2. 把一张待审批申请驳回；另建一张撤回；再尝试处理终态，核对错误与事件数。
3. 对6800元紧急申请，先用主管尝试，再用合法岗位决定，解释差异。
4. 刷新页面按原申请号查询；停服务再启动同一副本库，核对记录仍在。
5. 独立实现已有的“原因至少12字符”变式。自己选择11/12/500/501及首尾空格样本，至少提供一个HTTP和一个直接SQL的条件拒绝结果。若库已升级过，说明你验证的是新基线副本还是下一版本迁移，不能混称。

交付：自己的设计、源码差异说明、运行命令、实际请求/SQL与当前check --variant报告；写清参考了什么、哪些部分独立完成。报告通过不替代解释或独立性证据。

### 任务D：定位一个有竞争假设的故障

组织者提供同一系统的一个独立诊断副本，症状为“提交返回201，后续查询却不符合所填紧急信息”。不要先展开附录的故障位置。

先列两个可能原因及各自的可观察差异，再选择最少的请求或SQL区分它们。记录：

- 先看到什么，为什么检查这一层；如何确认请求确实发送了新字段。
- 哪个结果排除了另一个假设；具体修正了哪里。
- 重验是否恢复新字段，并保留原岗位/状态链路。

业务路线可只给诊断顺序和证据要求；工程路线在副本复现并修正。若只知道“参考补丁能通过”却不能解释故障位置，记录为需要提示，不记独立定位。

### 任务E：闭卷解释与延迟复现

结束时不看参考，用自己的话解释一个自己曾预测错误或修改过的决定。说明证据支持什么、什么仍不知道，以及下一次如何验证。

条件允许时，间隔1–3天用新的虚构标题/金额重新做一次边界预测与一次读回；先不看旧稿，再核对。此安排由学习者与组织者自行约定，不是本站自动提醒或定时任务。
