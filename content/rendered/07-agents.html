07｜Agent 与工具调用：从回答问题到执行任务

学习目标：区分固定工作流与具有动态决策能力的 Agent；理解工具的输入输出、状态、权限与失败恢复；能设计一个带人工确认的多步任务。

什么时候“聊天”不够？

模型可以建议“把公开活动整理进日历”，但若没有日历工具权限，它并没有真的创建日程。语言输出和外部操作不是一回事。一个能够采取行动的系统，通常需要先理解任务，再读取所需信息、选择工具、构造参数、处理结果，必要时请求用户确认，然后才执行不可逆操作。

例如用户说：“查看下周图书馆公开讲座，如果与已有日程不冲突，就帮我加入日历。”系统需要：查讲座公告 → 获取日期与地址 → 查询日历可用时间 → 展示候选日程 → 取得确认 → 创建日历事件 → 核对返回事件 ID。任何一步失败都可能要求停止或回退，而不是继续“假装完成”。

Workflow 与 Agent 的区别

固定工作流的路径由开发者事先规定，例如“表单提交 → 校验 → 保存 → 邮件通知”，其中某些节点可以调用 LLM。Agent 类系统则可能根据环境反馈动态选择下一步工具、参数或路径。不过边界并不绝对，很多成熟产品采用外层固定安全流程＋内部受约束 Agent。不是多调用一次 API 就一定有自主规划能力，也不是“Agent”标签就代表可靠。

目标 → 计划/下一步选择 → 工具调用 → 外部结果
          ↑                            ↓
          └────── 观察、校正或停止 ←───────┘
                     ↓
                  最终交付

工具描述就是执行合同

一个 calendar.create_event 工具至少要明确：事件标题、开始时间、结束时间、时区、参与者、是否发送邀请。调用前需要验证时间合法、参与者权限、日历冲突与用户确认。调用后应检查服务返回是否成功，而不是因为函数名含 create 就报告“已创建”。

对外部工具，应区分读操作与写操作。搜索活动安排是读；创建或删除日历事件是写。一个稳健的设计可以规定：模型自由选择低风险查询，但关键写操作需要显式批准。即使自动调用获准，也要限制作用域与参数范围。

常见失败与恢复

失败 正确响应思路 不应该做什么
日历 API 超时 查询操作是否成功，再决定是否重试 盲目重复创建导致重复日程
活动日期不明确 请求澄清或标记为待确认 猜一个日期直接提交
没有写入权限 明确告知无法执行，提供人工方案 声称已经创建成功
工具返回不可信网页文本 将其作为数据做解释与核验 让网页内容替代更高权限指令
部分成功 汇总实际完成部分并说明未完成项 把部分完成包装为全部完成

规划不是越长越好

复杂任务确实需要分解，但流程越长，越容易受到某个步骤失败的影响。能够确定的步骤应由程序稳定执行；需要文本理解或选择的步骤再交给模型。设计时先识别“必须变动的环节”，不要把固定的表单校验也交给自由推理。

对多步任务特别重要的是状态管理。系统需要知道已查到什么、哪些权限获批、哪个工具调用完成、是否重试过、最终证据是什么。用户在第六步说“不要发邀请”时，系统应能调整计划并保留此前合理的只读结果，而不是重头重复所有查询。

真实可验证的 Agent 小项目

设计一个“读者活动安排助手”原型，数据来自五条自制公开活动信息，工具用可控的本地函数模拟：search_events、find_free_slots、prepare_event、commit_event。其中 commit_event 必须显式接收 approved=true 才能改动本地测试日历。程序中保留每一步的工具调用日志。

设置四类测试：日期正确且无冲突、日历有冲突、活动已取消、用户未批准写入。确保最后一种测试里不会出现任何日历新增，并核对有冲突时能解释冲突来源。随后模拟一次“创建请求超时但实际已成功”，使用唯一请求 ID 或读回确认防止重复写入。

交付要求：工具输入输出 Schema、权限矩阵、一次正常轨迹、两次失败轨迹、创建后的事件标识。可以增加模型来选择调用顺序，但对写入批准和参数校验仍应由应用程序执行。

核心回忆问题

  1. 为什么“帮你建好了”这一句回复不能证明日历事件存在？
  2. 哪个步骤应该由模型灵活选择，哪个步骤必须由确定性程序控制？
  3. 工具超时后为什么不能直接重试一次写操作？
